---
name: contract
description: Write an ODCS (Open Data Contract Standard) v3.0, v3.1, or v3.2 data contract for a PBIP semantic model (starting from its TMDL), and turn it into PQL.Assert DAX test suites, report which contract rules are enforced, run them, and trace failures back to contract rule ids.
version: 0.2.0
---

`pql-test contract` turns an ODCS data contract's quality rules into PQL.Assert `*.Tests.dax` suites. It reports every rule as mapped, approximated, or skipped, so no rule is silently dropped. The commands come with `pip install pql-test`. `run` and `doctor`'s live checks need XMLA (Windows); `lint`, `coverage`, `generate`, and `trace` only read and write files, so they also run on Linux, for example in CI.

## Behavioral Contract

```sudolang
Interface Contract {
  init MODEL_PATH [--output FILE]          // starter contract from the model's TMDL: tables, columns, types
  generate CONTRACT MODEL_PATH --env ENV   // writes <Prefix>.<Suite>.<ENV>.Tests.dax into MODEL_PATH/DAXQueries/
  coverage CONTRACT [--format text|json]   // every rule: mapped | approximated | skipped (+ reason)
  lint CONTRACT [MODEL_PATH]               // ODCS schema validation + every name resolves
  trace CONTRACT RESULTS_JSON              // joins `pql-test run-tests --output` JSON to contract rule ids
  run CONTRACT MODEL_PATH --env ENV        // generate in memory, run, then trace; writes no files (--write also saves them)
  doctor [MODEL_PATH]                      // environment, the model's PQL.Assert library, the deployed or open model

  exit_code: 0 | 1 | 2
    // 0 = success
    // 1 = contract invalid, lint problems, --fail-on-skipped triggered, a failed doctor check, or (run) a blocking suite failed / nothing ran
    // 2 = usage error: bad --env token, MODEL_PATH not a PBIP model, or a file pql-test would overwrite without --force
}

Constraints {
  MODEL_PATH is the same in every contract command: a PBIP folder (the root with the .pbip file, or the
    *.SemanticModel folder), a .pbip file, or local/<name>, which means the one <name>.SemanticModel in this repository.
    With local/<name>, `run` and `doctor` connect only to that model open in Power BI Desktop, even when PQL_* service
    credentials are set; --model-dir picks the folder when the repository holds several copies (doctor, run --write).
  `run` never changes the PBIP project or the model: suites are built in memory and run as read-only queries.
    Writing into DAXQueries/ (and so into git and Fabric Git integration) is a separate act: generate, or run --write
    <workspace>.Workspace/<model>.SemanticModel is NOT accepted yet
  Suites are named <Prefix>.<Suite>.<ENV>.Tests, where Suite is Schema, DataQuality, ContractDax (engine: pql-test rules),
    or RefreshAge (frequency SLAs);
    the prefix comes from the contract's dataProduct, then its name (override with --suite-prefix)
  severity: warning (or info) rules go to separate <ENV>WARN suites: reported, but they never fail `run`
  Test names are "ODCS <contractId> <ruleId>: <description>"; ruleId is the ODCS `id`, else a path like orders.customer_id.quality[0]
  Generated files start with "// Generated by pql-test" and name their contract id; generate refuses to overwrite a hand-written file
    or another contract's suite (same prefix) unless --force; give contracts that share a dataProduct distinct --suite-prefix values
  --pql-assert 0.7|0.8 picks the PQL.Assert version generated for (default 0.7; `run` defaults to auto: it asks the model
    with PQL.Assert.LibraryVersion() and falls back to 0.7); 0.8 needs a model with PQL.Assert 0.8.0 or later
  approximated = generated, but DAX semantics differ (named in the reason): primaryKey/unique/duplicateValues are skewed by blanks;
    required on string columns also counts empty strings as nulls (0.7); text value lists ignore case; latency and frequency
    depend on when the test runs
  latency and frequency are different SLAs. latency (element table.column, a load timestamp) checks data age: the newest value
    in the model. frequency (element table) checks refresh recency: INFO.PARTITIONS()[RefreshedTime], in the RefreshAge suite.
    A successful refresh of stale source data passes frequency and fails latency, so recommend both, and a load timestamp,
    never a business date, for latency; latency on a table with no column is skipped (refresh time is not source latency)
  type: custom rules with engine: pql-test carry DAX: implementation {expression, <one comparator>} or {function, args}.
    pql-test supplies testName; the function form needs --pql-assert 0.8. The DAX must be one expression (no EVALUATE or
    DEFINE, balanced brackets and quotes, no comma outside brackets, no control characters but line feed and tab);
    lint reports a rule that breaks this. On --pql-assert 0.7 a BLANK result passes text mustBe and number comparisons
    (approximated). Coverage JSON marks these rules "source": "contract-dax". Never use type: sql for DAX (other tools
    would run it as SQL)
  Both workflows are supported: regenerate in CI (`contract run`, which writes no files), or commit the generated
    suites and fail CI on drift (`generate` then `git diff --exit-code`); see docs/contracts.md
  run --output adds a "contract" key (per-rule trace) to the run-tests JSON; run --log-format emits one annotation per failed rule
  Model names come only from the contract: customProperties pbiTable (schema object) / pbiColumn (property), else the ODCS logical name;
    customProperties pbiDataType (property) pins the exact model type for the column type check (Text, Integer, Number, Currency, Date, True/False, Binary);
    there is no sidecar mapping file
  Never claim a rule is enforced when coverage reports it skipped; quote the reason instead
}
```

## Writing a contract

Start from the model instead of a blank file. `init` reads the PBIP model's TMDL and writes a starter contract: one schema object per table, one property per column, and each column's `logicalType`. It only reads the model. The starter states what the model already is, so it lints clean and passes as is; the rules worth having are the ones you add on top.

```
pql-test contract init ./MyModel --output mymodel.odcs.yaml                        # every table
pql-test contract init local/MyModel --table Sales --table Customer -o sales.odcs.yaml
```

`init` options: `--table NAME` (repeatable, any case), `--id ID` (default: the model name, lowercased with dashes), `--output FILE` / `-o` (default: stdout), and `--force` to overwrite the `--output` file. It leaves out measure tables (only measures, or only hidden placeholder columns) and Power BI's automatic date tables. A column with no ODCS type (a calculated table or column, or `binary`) gets a `description` saying why instead of a `logicalType`.

`examples/contracts/` has three runnable contracts against `examples/SampleModel`, each verified to pass every mapped rule: `starter.odcs.yaml` (init's own output), `scenario-tests.odcs.yaml` (engine: pql-test DAX rules, both forms), and `freshness.odcs.yaml` (latency and frequency).

Then add the rules the data must meet, on the property or the schema object:

```yaml
apiVersion: v3.1.0
kind: DataContract
id: sales
version: 1.0.0
status: draft
schema:
  - name: Sales                      # the model table (or set customProperties pbiTable)
    physicalType: table
    properties:
      - name: OrderID
        logicalType: integer         # checked against the column's model type
        required: true               # no nulls
        primaryKey: true             # distinct, no nulls
      - name: Amount
        logicalType: number          # Number or Currency; pin one with pbiDataType
        quality:
          - metric: nullValues
            mustBeLessOrEqualTo: 5
            unit: percent            # --pql-assert 0.8
    quality:
      - metric: rowCount
        mustBeGreaterThan: 0
```

Rules pql-test maps are listed below; any other rule is reported as skipped with its reason, never enforced. Use `customProperties` `pbiTable` / `pbiColumn` only when the ODCS name differs from the model name, and `pbiDataType` to pin an exact model type.

Work in this loop, and fix each step before the next:
1. `pql-test contract init MODEL --output c.odcs.yaml`
2. edit the rules
3. `pql-test contract lint c.odcs.yaml MODEL` — valid ODCS, names and types match the model
4. `pql-test contract coverage c.odcs.yaml --pql-assert 0.8` — what is enforced, approximated, or skipped
5. `pql-test contract run c.odcs.yaml MODEL --env DEV` — run it against the model (writes no files)

Scenario tests (a measure's value in a filter context) and freshness go in the same contract:

```yaml
schema:
  - name: Sales
    quality:
      - id: no-sales-is-zero                   # a scenario: 0, not blank, when nothing matches
        type: custom
        engine: pql-test
        implementation:
          expression: CALCULATE([Total Sales], 'Date'[Year] = -1)
          mustBe: 0
      - id: amount-mean                        # any PQL.Assert check, by name (--pql-assert 0.8)
        type: custom
        engine: pql-test
        implementation:
          function: PQL.Assert.Col.MeanShouldBeInRange
          args: ["'Sales'[Amount]", 0, 500]
slaProperties:
  - property: latency                          # data age: the newest load is at most 3 hours old
    value: 3
    unit: h
    element: Sales.LoadedAtUtc
  - property: frequency                        # refresh recency: the model refreshed in the last 26 hours
    value: 26
    unit: h
    element: Sales
```

## What the default `--pql-assert 0.7` maps

| ODCS rule | Generated check |
|---|---|
| Schema object present | `Tbl.ShouldExist` |
| Properties present | `Tbl.ShouldHaveColumns` (one per table) |
| `--closed-schema` | `Tbl.ShouldNotHaveExtraColumns` |
| `logicalType` string / integer / number / boolean | `Tbl.ColumnDataTypeShouldBe` with Text / Integer / Number or Currency / True/False; date, timestamp, and time check Date (approximated) |
| `required: true`, `nullValues mustBe 0` | `Col.NullRateShouldBeAtMost(…, 0)` (approximated on string columns) |
| `primaryKey`, `unique`, `duplicateValues mustBe 0` | `Col.ShouldBeDistinct` (one shared check per column; approximated, because blanks skew it) |
| `rowCount` (all comparators except `mustNotBeBetween`) | `Tbl.ShouldHaveRows` / `ShouldHaveRowCount` / `ShouldHaveMoreRowsThan` / comparisons on `COUNTROWS` |
| `type: custom`, `engine: pql-test`, `implementation.expression` | `ShouldEqual` (text: `ShouldEqualExactly`) / `ShouldNotEqual` / `ShouldBeGreaterThan` / ... / `ShouldBeBetween` on the expression |

Everything else is reported as **skipped**, with the release that will map it:
- `type: sql` and `text` rules, `type: custom` for any engine but `pql-test`, and the `pql-test` direct-call form;
- composite keys, nested properties, and ODCS 3.2 `map` / `vector` properties;
- `logicalTypeOptions`, relationships, ODCS 3.2 `enum`, and a `physicalType` with no `logicalType`;
- `missingValues` and `invalidValues`;
- non-zero thresholds;
- SLA properties.

With `--pql-assert 0.8` (needs PQL.Assert 0.8.0 or later in the model), more rules map exactly:
- `required: true` and `nullValues` use `Col.NullCountShouldBeAtMost`, which counts true nulls only; empty strings are not nulls;
- `nullValues` with an absolute ceiling, or `unit: percent` (`Col.NullRateShouldBeAtMostV2`);
- `primaryKey` uses `Col.ShouldBePrimaryKey`; `unique` and `duplicateValues mustBe 0` use `Col.NonNullValuesShouldBeDistinct` (nulls ignored);
- composite `primaryKey` and schema-level `duplicateValues` over two or more properties use `Tbl.RowsShouldBeDistinct`;
- `duplicateValues` with a ceiling uses `Col.DuplicateCountShouldBeAtMost`, and `rowCount mustNotBeBetween` uses `ShouldNotBeBetween`;
- simple patterns (`^literal`, `literal$`, a bare literal) use `Col.ShouldStartWith` / `ShouldEndWith` / `ShouldContainString`, case-sensitive like the regex;
- `logicalTypeOptions` bounds use `Col.ShouldBeInRange` / `MinShouldBeAtLeast` / `MaxShouldBeAtMost` / `ShouldBePositive` (an integer's exclusive bound converts exactly), and `minLength` / `maxLength` use `Col.TextLengthShouldBeInRange`;
- ODCS 3.2 `enum` and `invalidValues` with `validValues` use `Col.ValuesShouldBeInSet`, or `Tbl.RowCountShouldBeAtMost` / `RowRateShouldBeAtMost` with a threshold; `missingValues` (default null and `""`) uses the same row checks;
- `relationships` (foreign keys between contract properties) use `Relationship.ShouldExist`, and `lint` checks them against the model's TMDL;
- a `latency` SLA with `table.column` element(s) uses `Col.MaxDateShouldBeWithinDays` / `…Hours` (data age), and a `frequency` SLA with a table element checks the hours since the last refresh (refresh recency); both are approximated;
- `engine: pql-test` rules can also call any PQL.Assert assertion directly (`implementation: {function, args}`).

Options shared by `generate`, `coverage`, and `run`:
- `--env ENV` — environment token for suite names, e.g. `DEV` (generate/run; required).
- `--suite-prefix NAME` — override the suite name prefix.
- `--closed-schema` — also fail when a table has columns the contract does not list.
- `--pql-assert 0.7|0.8` — PQL.Assert version to generate for (`run` also accepts `auto`, its default).
- `--fail-on-skipped` — exit 1 when any rule is skipped (generate/coverage; strict CI).
- `--dry-run` — print the DAX instead of writing files (generate).
- `--force` — overwrite suite files that pql-test did not generate (generate, run --write).

Every contract command takes `-v/--verbose` and `-q/--quiet` (only the summary line; a result on stdout, such as JSON, a contract, or DAX, is never suppressed), and every command with a report takes `--format text|json`, `lint` included. `-o` is short for `--output`.

`doctor [MODEL_PATH]` checks the environment and, with a PBIP model, the PQL.Assert library in its TMDL and in the deployed or open model. It recommends a `--pql-assert` value, warns when the deployed model supports a different one, and exits 1 when a check fails. It accepts `--format json`, `--model-dir`, and the same connection options as `run`.

`run` also accepts `--write` (also save the suites into DAXQueries/), `--format json` (the JSON results on stdout), `--output FILE`, `--log-format azuredevops|github`, and, with `--write`, `--model-dir DIR` (the PBIP folder of a `local/<name>` MODEL_PATH), plus the connection options of `run-tests`: `--tenant-id`, `--workspace-id`, `--dataset-id`, `--client-id`, `--client-secret`.

Usage:
```
# Check the model's PQL.Assert library, locally and deployed, and which --pql-assert to use
pql-test contract doctor ./MyModel

# See which contract rules can be enforced before generating anything
pql-test contract coverage orders.odcs.yaml

# Check the contract and that every table/column exists in the model
pql-test contract lint orders.odcs.yaml ./MyModel

# Write the suites into the PBIP model's DAXQueries/ folder
pql-test contract generate orders.odcs.yaml ./MyModel --env DEV

# Generate in memory, run, and trace in one step; writes no files
pql-test contract run orders.odcs.yaml ./MyModel --env DEV

# The same against the model open in Power BI Desktop, even when PQL_* service credentials are set
pql-test contract run orders.odcs.yaml local/MyModel --env DEV

# CI: GitHub annotations, JSON results, and fail if any rule cannot be enforced
pql-test contract coverage orders.odcs.yaml --fail-on-skipped
pql-test contract run orders.odcs.yaml ./MyModel --env DEV --output results.json --log-format github

# Trace an earlier run-tests result file back to contract rule ids
pql-test run-tests ./MyModel --env DEV --output results.json
pql-test contract trace orders.odcs.yaml results.json
```
