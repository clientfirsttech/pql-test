# pql-odcs

Generate [PQL.Assert](https://github.com/clientfirsttech/PQL.Assert) DAX test suites from [ODCS](https://bitol-io.github.io/open-data-contract-standard/) v3.0, v3.1, and v3.2 data contracts. Every contract rule is reported as **mapped**, **approximated**, or **skipped**, so nothing is dropped silently. Failures from a test run can be traced back to the contract rule that produced them.

pql-odcs is MIT-licensed, has three runtime dependencies (PyYAML, jsonschema, click), and runs on Linux, macOS, and Windows. It only produces text (DAX). To run the generated suites against a semantic model, use [pql-test](https://github.com/clientfirsttech/pql-test), which mounts these same commands as `pql-test contract …` and adds `pql-test contract run`.

## Install

```bash
pip install pql-odcs              # standalone CLI: pql-odcs
pip install "pql-test[contracts]" # pql-test with `pql-test contract …`, including `run`
```

## Quick start

```bash
pql-odcs coverage orders.odcs.yaml                              # which rules can be enforced?
pql-odcs lint orders.odcs.yaml --model ./SalesModel             # contract valid, names resolve?
pql-odcs generate orders.odcs.yaml ./SalesModel --env DEV       # write *.Tests.dax suites
pql-test run-tests ./SalesModel --env DEV --output results.json # run them (pql-test)
pql-odcs trace orders.odcs.yaml results.json                    # failures by contract rule id
```

## Commands

| Command | What it does |
|---|---|
| `generate CONTRACT MODEL_PATH --env ENV` | Writes `<Prefix>.<Suite>.<ENV>.Tests.dax` into the PBIP model's `DAXQueries/` folder |
| `coverage CONTRACT [--format text\|json]` | Lists every rule with its status, generated function(s), and skip reason |
| `lint CONTRACT [--model MODEL_PATH]` | Validates against the bundled ODCS JSON schema, then checks that names resolve and (with `--model`) that every table and column exists in the model's TMDL |
| `trace CONTRACT RESULTS_JSON` | Joins pql-test `--output` JSON to rule ids: passed, failed, error, not executed, or skipped |

**Shared flags**:
- `--closed-schema` also forbids columns the contract does not list.
- `--fail-on-skipped` exits 1 if any rule is skipped (`generate`, `coverage`).
- `--suite-prefix NAME` overrides the suite prefix (`generate`, `trace`).
- `--dry-run` prints the DAX instead of writing files (`generate`).
- `--force` overwrites suite files that pql-odcs did not generate (`generate`).

**Exit codes**:
- 0 means success.
- 1 means the contract is invalid, `lint` found problems, or `--fail-on-skipped` was triggered.
- 2 means a usage error: a bad `--env` token, a MODEL_PATH that is not a PBIP folder, a file pql-odcs would refuse to overwrite, or an unreadable results file.

In v0.1, `MODEL_PATH` must be a PBIP folder: the root containing the `.pbip` file, the `*.SemanticModel` folder, or the `.pbip` file itself. Query-scoped XMLA runs (`--target query`) arrive in v0.2, and persistent deploys (`--target deploy`) in v0.3.

## Generated suites

- **Names**: `<Prefix>.<Suite>.<ENV>.Tests`. `Suite` is `Schema` (tables and columns) or `DataQuality` (everything else). The prefix is a PascalCase form of the contract's `dataProduct`, then its `name`, then its `id`. pql-test matches `ENV` as the second-to-last dotted token, so `pql-test run-tests --env DEV` picks the suites up.
- **Warning rules**: rules with `severity: warning` or `info` go into separate `<Prefix>.<Suite>.<ENV>WARN.Tests` suites. CI can run these without failing the build, and `pql-test contract run` never fails on them.
- **Test names**: `ODCS <contractId> <ruleId>: <description>`. The rule id is the ODCS `id` when it is unique in the contract; otherwise it is a stable path such as `orders.customer_id.quality[0]`. Descriptions use the contract's own names.
- **Header**: every file starts with `// Generated by pql-odcs <version> from <contract> — do not edit`, followed by a line naming the contract id. `generate` refuses to overwrite a hand-written file, or a suite generated from a **different contract** that has the same prefix, unless you pass `--force`. It deletes a suite only when this contract generated it in an earlier run and it no longer has any rules. Give two contracts that share a `dataProduct` distinct `--suite-prefix` values.
- **Line endings**: output is deterministic, with LF line endings, so the files can be committed and diffed.

The generated DAX calls PQL.Assert, which must be installed in the model, version 0.7.1 or later (DAX Lib).

## Commit the suites, or regenerate them in CI?

pql-odcs supports both workflows. Pick one per model repository.

| | Regenerate in CI | Commit to the PBIP repo |
|---|---|---|
| Source of truth | The contract alone | The contract, plus the generated files |
| Drift | Impossible: suites are rebuilt on every run | Possible, so CI must check for it (below) |
| Visible in Power BI Desktop's DAX query view | Only after a local `generate` | Yes |
| Published with the model (Fabric git integration) | No | Yes, as files in `DAXQueries/` |
| Counted by `pql-test code-coverage` | No | No: files in `DAXQueries/` are not model functions. Persistent deploy arrives in v0.3. |
| Review | Review the contract | Review the contract and the DAX diff |

**Regenerate in CI.**
1. Don't commit the generated files. Ignore them by prefix, for example in `.gitignore`: `**/DAXQueries/Marvel.*.Tests.dax`.
2. In CI, run one step, which generates, runs and traces:
   ```bash
   pql-test contract run orders.odcs.yaml ./SalesModel --env DEV --output results.json --log-format github
   ```

**Commit to the PBIP repo.**
1. Run `pql-odcs generate … --env DEV` whenever the contract changes, and commit the output.
2. Add a CI step that fails when the committed suites are stale:
   ```bash
   pql-odcs generate orders.odcs.yaml ./SalesModel --env DEV
   git diff --exit-code -- '*/DAXQueries/*.Tests.dax'
   ```

Generated files carry the pql-odcs version in their header, so upgrading pql-odcs also shows up as a diff. Regenerate and commit after an upgrade.

Both workflows are safe to mix with hand-written suites in the same `DAXQueries/` folder. `generate` never overwrites a file it did not generate, or a suite generated from another contract.

## Name resolution

Each ODCS schema object maps to a semantic model table, and each property to a column. The model names live in the contract itself, using ODCS's own extension mechanism, `customProperties`. That keeps them valid on ODCS 3.0, 3.1 and 3.2, and keeps them with the contract wherever it goes (including the datacontract-cli adapter):

```yaml
schema:
  - name: fact_marvel
    customProperties:
      - property: pbiTable          # semantic model table
        value: MarvelFact
    properties:
      - name: eye_id
        customProperties:
          - property: pbiColumn     # semantic model column
            value: EyeID
```

When `pbiTable` or `pbiColumn` is absent, the ODCS logical `name` is used unchanged. `lint --model` checks that every resolved table and column exists in the model's TMDL.

## Rule mapping (v0.1)

| ODCS rule | PQL.Assert 0.7.1 call | Status |
|---|---|---|
| Schema object present | `Tbl.ShouldExist` | mapped |
| Properties present | `Tbl.ShouldHaveColumns` (one call per table) | mapped |
| Closed schema (`--closed-schema`) | `Tbl.ShouldNotHaveExtraColumns` | mapped |
| `required: true`, `nullValues mustBe 0` | `Col.NullRateShouldBeAtMost(…, 0)` | mapped; **approximated** on `string` columns (DAX treats empty strings as BLANK, so they count as nulls) |
| `primaryKey`, `unique`, property `duplicateValues mustBe 0` | `Col.ShouldBeDistinct` (one call per column, shared by every rule that asks for it) | **approximated**: it compares `DISTINCTCOUNT` (counts BLANK) with `COUNTA` (ignores blanks). A blank fails an otherwise distinct column, and one blank plus one duplicate still passes. See [PQL.Assert gap plan](https://github.com/clientfirsttech/pql-test/blob/main/docs/pql-assert-gap-plan.md) C4. |
| `rowCount mustBeGreaterThan 0` | `Tbl.ShouldHaveRows` | mapped |
| `rowCount mustBe n` | `Tbl.ShouldHaveRowCount` | mapped |
| `rowCount mustBeGreaterThan n` | `Tbl.ShouldHaveMoreRowsThan` | mapped |
| `rowCount` `mustNotBe`, `mustBeGreaterOrEqualTo`, `mustBeLessThan`, `mustBeLessOrEqualTo`, `mustBeBetween` | `ShouldNotEqual`, `ShouldBeGreaterOrEqual`, `ShouldBeLessThan`, `ShouldBeLessOrEqual`, `ShouldBeBetween` on `COUNTROWS` | mapped |

`Col.ShouldNotBeNull` is not used for `required`. In PQL.Assert 0.7.1 it passes when any value is non-null.

These rules are reported as **skipped**, with the release that will map them:

| ODCS rule | Planned |
|---|---|
| Column types (`logicalType` / `physicalType`) | v0.2 (`Tbl.ColumnDataTypeShouldBe`) |
| `logicalTypeOptions` minimum/maximum, minLength/maxLength | v0.2 |
| `logicalTypeOptions` pattern, `invalidValues` with a pattern | v0.3 |
| v3.1 `relationships` | v0.2 (`Relationship.ShouldExist`) |
| v3.2 `enum` (allowed values) | v0.2 (`Col.ValuesShouldBeInSet`) |
| `nullValues` percent or absolute thresholds | v0.2 |
| `missingValues`, `invalidValues` | v0.2 |
| Composite primary keys, 2- and 3+-column `duplicateValues` | v0.2 |
| `rowCount mustNotBeBetween` | v0.2 |
| Non-zero `duplicateValues` thresholds | v0.3 |
| Nested (object / array) and v3.2 `map` / `vector` properties | no model column |
| `type: sql` | later (optional, review-marked DAX stub) |
| `type: custom`, `type: text`, `slaProperties` | not planned |

ODCS v3.0 contracts that use `rule:` instead of `metric:` are understood: `nullCheck` is read as `nullValues`, `duplicateCount` as `duplicateValues`, and `validValues` as `invalidValues`.

## Python API

```python
from pql_odcs.api import plan_contract, render, generate
from pql_odcs.coverage import build_report
from pql_odcs.results import trace

plan = plan_contract("orders.odcs.yaml")  # or an already-parsed dict
files = render(plan, env="DEV")  # list of SuiteFile(function_name, content, blocking)
report = build_report(plan.contract, plan.outcomes)
```
